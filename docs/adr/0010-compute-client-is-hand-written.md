# ADR-0010 — The Compute client is hand-written against the observed wire shape, not a vendored generated client

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decides:** how the extension talks to the SAS Viya Compute service, reversing
  the vendoring approach `PRODUCTION_PLAN.md` pre-agreed for slice 2a
- **Executed in:** slice `2a-i`

## Context

The plan has said since it was written that Phase 2a would follow upstream and
vendor the generated OpenAPI client:

> **Pre-agreed split if the diff is unreviewable:** `2a-i` vendors the generated
> OpenAPI client (large but mechanical), `2a-ii` adds the hand-written session
> and link layer.

That was a reasonable default. Upstream ships such a client, it is checked in and
working against real deployments, and copying it is a mechanical diff that a
reviewer can skim rather than read. The alternative — writing a client by hand
against a service we do not control — trades a day of copying for an ongoing
maintenance obligation, and the plan chose not to take that on speculatively.

ADR-0009 then flagged that this choice collides with the coverage rule, and named
the three ways out:

> When 2a-i comes, the choice is between keeping the client in the denominator
> and accepting the number, placing it outside `src/` so it is not a source file
> at all, or amending this ADR with a second rule that argues its case.

Before writing the 2a punchlist, two things were measured that were not known
when either document was written: what upstream's client actually contains, and
what the Compute service actually puts on the wire. Both point the same way, and
neither is one of ADR-0009's three options. The answer is a fourth: there is no
client to exclude, because we are not vendoring one.

### What the vendored client contains

`client/src/connection/rest/api/` in the upstream clone is **28,673 lines** in
five files — `compute.ts` at 20,348 (715 KB), `files.ts` and `folders.ts` at
4,024 each, and two small support files.

`compute.ts` exposes **136 operations**. The session layer that consumes it calls
**twelve**. Counting every adjacent adapter in the upstream extension — libraries,
servers, the lot — the total reaches 28, or about a fifth. `files.ts` and
`folders.ts`, 8,048 lines together, are imported by **nothing**: the content
adapter that would have used them talks to a raw `axios.create()` instead. So
roughly 26,000 of the 28,673 vendored lines never execute, and about 20,000 of
them never execute in any upstream code path either.

The client is generated by OpenAPI Generator's `typescript-axios` template and
its only transport is `globalAxios.request`. Vendoring it therefore reintroduces
**axios**, which ADR-0008 removed in favour of `https.request` after a specific
argument about system certificate trust. It has also been **checked in and never
regenerated** since 2022 — there is no generator invocation and no OpenAPI
document anywhere in the upstream repository — so the property that makes a
generated client attractive, that it can be regenerated when the service moves,
is not one upstream actually has. It is hand-maintained code that looks
generated, which is the worst of both.

### What the service actually puts on the wire

The probe of 2026-08-14 (`PROBE-FINDINGS.md`, findings 10–17, run against a live
Viya 4 at cadence LTS 2026.03) established three things that bear directly on
this.

**The service is navigated by links, not by constructed URLs.** Every
representation carries a `links` array, and every operation the session layer
needs — create a session, execute, read state, delete, page a log — is reachable
by finding a `rel` and following its `href`, `method`, `type` and `responseType`.
A generated client's value is that it writes 136 URL builders for you. We need
approximately one, because the server sends us the rest.

**A generated client is not sufficient on its own anyway.** Link `type` values
arrive as the bare vendor media type — `application/vnd.sas.compute.job.request`
— and the service requires `+json` appended before it will accept them. That rule
is a property of the responses, not of any specification, which is precisely why
upstream had to hand-write `computeMediaType()` and take a dependency on
`media-typer` to sit *alongside* its generated client. The same is true of the
`If-Match`/`If-None-Match` policy and of the `wait` long poll. The hand-written
layer is not the small part; it is where all the behaviour lives.

**The one wart the plan singled out is caused by the vendoring.** Upstream's
`link.href.replace("/compute", "")` exists only because the generated client
wants a `basePath` and upstream set it to `endpoint + "/compute"`, while the
service's own hrefs are deployment-root-relative and already carry the prefix. So
each href is mutilated on the way out to undo a prefix that should never have
been added — with `String.replace`'s first-occurrence-anywhere semantics, and as
a 2022 regression from an anchored `slice`. The plan lists fixing it as a 2a
deliverable. Not vendoring deletes its cause rather than patching its effect.

### What hand-writing costs

Measured against the twelve operations the session layer uses: a request helper
of 80–100 lines, around eleven narrow response interfaces at 120–150, and the
operations themselves at 120–150 — call it **350–450 lines** where the generated
file is 20,348. Adding the link, ETag and media-type base and the session and job
orchestration that upstream hand-writes regardless brings the whole layer to
roughly **800–1,000 lines**, replacing 20,348 generated plus 1,223 hand-written.

## Decision

**Write the Compute client by hand, against the wire shape recorded in
`PROBE-FINDINGS.md`, on the `https.request` transport ADR-0008 settled.**

Model only the fields the extension reads. Navigate by link relation rather than
by constructed path, storing the deployment **origin** as the only base and
resolving every `href` against it, so no URL is ever rewritten. Capture the
request and response shapes as scrubbed fixtures from live probes, and test
against those fixtures rather than against a specification we do not have.

`PRODUCTION_PLAN.md`'s pre-agreed 2a split is replaced in the same pull request:
`2a-i` is now the pure core with no `vscode` import, `2a-ii` the VS Code shell,
matching the shape 1b and 1c both used.

ADR-0009 is **not** superseded. Its rule is unchanged and its warning was
correct; this decision removes the pressure on it rather than bending it. The
three options it named remain the right three should a vendored client ever be
proposed again.

## Alternatives considered

**Vendor the generated client as planned.** Rejected on four counts, any one of
which would have been arguable alone. It reintroduces axios against ADR-0008. It
adds ~20,000 lines to the coverage denominator, which is exactly the pressure
ADR-0009 was written to resist, and the only ways to relieve it are the three
options ADR-0009 named — each of which is a concession made to accommodate code
that never runs. It brings NOTICE and licence-header obligations for generated
third-party output through `check:copyright`, and it inflates a VSIX that
`check:package` currently measures in kilobytes. And it does not remove the need
for the hand-written layer, so the cost is paid on top of, not instead of, the
work.

**Vendor and then trim to the used surface.** Superficially the best of both: the
shapes still come from the specification, at a fraction of the size. Rejected
because a trimmed generated file can never be regenerated, so the one durable
advantage is destroyed by the trimming itself. What remains is hand-maintained
code carrying a "do not edit, this file is generated" banner — an instruction
that is now false, in a file a future reader will believe. It also still has to
be converted off axios, at which point very little of the original is left.

**Generate at build time from an OpenAPI document.** The honest version of
vendoring: keep the specification, regenerate on demand. Rejected because there
is no specification to keep. Upstream's repository contains no OpenAPI document
and no generator invocation, so the source would have to be fetched from a
deployment and pinned; and OpenAPI Generator itself is a Java toolchain, which is
a build-time dependency of a different order from anything in this project today
and sits awkwardly against ADR-0005. This would be a slice of its own, taken on
to avoid writing 400 lines.

**Use upstream's hand-written layer as-is and vendor only what it imports.** The
narrowest vendoring. Rejected because the hand-written layer is the part that
most needs rewriting rather than porting: the process-global mutable
`Configuration` singleton that makes two simultaneous connections structurally
impossible, `getPKCE`'s `Math.random()`, the unbounded recursion in `cancel()`
and `getState()`, an `Error` thrown with no message, and a dead `context.ts` that
passes the wrong argument type. Those are catalogued in `PROBE-FINDINGS.md` and
the auth audit. Porting the 12 operations is the easy half.

## Consequences

**We own the request and response types, and they can drift.** This is the real
cost and it should be read as one. A deployment that adds a field we do not model
is harmless — we read what we name — but one that *renames* or removes a field we
depend on breaks us, and no compile step will notice, because the types are ours
rather than the service's. Three things mitigate it and none eliminates it: the
live smoke test in `test/live/` exercises the real deployment; the fixtures are
captured from probes rather than invented, so they are wrong in the same ways the
service is; and navigating by link relation means path changes cannot break us at
all, which historically is how these services move. Modelling narrowly is part of
the mitigation, not a shortcut — every field we decline to model is a field that
cannot break us.

**The layer stays inside the coverage denominator, and that is the point.** It
imports no `vscode`, so under ADR-0009 it is measured, and at 800–1,000 lines of
pure logic it should raise the ratchet rather than threaten it. A vendored client
would have been 20,000 unreachable lines dragging it the other way.

**Viya 3.5 support gets easier, not harder.** A generated client is generated
from one deployment's specification and encodes that version's shape as types.
Hand-written narrow models plus link navigation express version differences the
way the service itself does — as media types and the presence or absence of a
link relation — which is the only mechanism available in a layer where upstream
has no version branching at all.

**`media-typer` is not a dependency.** The `+json` rule is a total function over
`string | null | undefined` with a table of cases in a unit test, including the
`text/plain` links that must not be suffixed and the `DELETE` links whose `type`
is `null` in one representation and absent in another.

**If this turns out to be wrong, the reversal is cheap.** The failure mode is
discovering we need many more operations than twelve, at which point vendoring
becomes attractive again on the same evidence that rejected it. Nothing here
forecloses that: the client is behind the link layer, the fixtures survive, and
ADR-0009's three options are still on the table. Reverse it with a new ADR rather
than by growing this one.
